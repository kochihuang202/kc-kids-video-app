# InkBridge 實作流程（使用者確認，2026-10-30）

目標是盡可能完整拷貝／重用 FlexNote 已有的程式與細節，形成獨立執行、資料隔離、可讀、可修改、可重新建置與維護的 InkBridge。不是追求每行都重新自行撰寫。M1/M2 的簡化底座不是最終產品。

**本次較晚確認的規則取代舊版「不搬原模組、全部自寫」及「查不到可自行設計補足」的方向；不得再援引舊句自行重寫。**

執行順序與證據要求以 [docs/DEVELOPMENT_WORKFLOW.md](docs/DEVELOPMENT_WORKFLOW.md) 為準：

1. 有未知、疑點或差距，先查既有 Gemini 清單／REA、原版程式及必要的針對性 REA；不要先猜、先換成自己熟悉的做法。
2. 能完整取得、確認可用且能修改的原模組與必要依賴，優先拷貝／重用，不為「全部自寫」而重新發明。先核對來源、適用條件、依賴、輸入輸出和重建方式；不能只搬局部演算法或參數而丟掉例外與互動細節。
3. 黑盒必須先用 REA 追查：可讀打包 JavaScript 追完整呼叫與依賴；原生／WASM 優先找對應版本公開原始碼，缺失再針對性逆向與還原。反編譯輸出、能啟動、能改幾行不等於完整可維護原始碼；未拆清的黑盒不得當完成。
4. 只有確實追不到合理可能來源時，提出已查來源／範圍、結果、限制、缺口、替代方案及影響，**先與使用者討論決定**。不得直接自行設計、簡化、替換、跳過或重寫。
5. 確認來源與規格後才改產品碼；修改前建立基線，修改後由工程代理自行啟動、操作、對照及回歸。不得要求使用者承擔大量人工驗證來補自行重寫的缺口。確實需要特定硬體／帳號／實體IME時，再明確說明剩餘人工項目。
6. 沿用 Gemini 與既有 REA 成果，同一原版／hash 的分析互相核對；有分歧回原碼確認，不各自猜一套，也不重複完整分析。
7. 保留獨立資料、設定與生命週期，不碰正式 FlexNote 資料；來源副本及重用候選先在隔離環境保存。不得繞過授權保護／完整性機制；不把原版二進位、專有原碼、token或私人筆記推送公開交付歷史。

沿用上層回歸、Git 同步與提交規則；只提交本次範圍，不納入同一工作目錄內其他專案的變更。

測試補充（使用者2026-10-30較晚指令）：**只測本次改動相關流程及歷史回歸，不每次整包全部重測。** 以實際影響範圍選維護中的spec／case；封裝驗證與效能抽查也只跑相關子集。新失敗／新修改才擴大範圍，不因共用模組自動全測。
