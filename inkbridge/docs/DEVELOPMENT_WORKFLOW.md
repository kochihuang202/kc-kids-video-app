# InkBridge：先確認原版，再重製

使用者於 2026-10-30（Asia/Taipei）確認：希望盡可能忠實重製 FlexNote；有問題先確認，只有查不到的部分才自行設計實作。本流程供後續 Codex／Gemini 工作延續，不把簡化 demo 視為完成。

## 固定順序

**既有研究／Gemini 功能清單 → 原版程式或針對性 REA 確認 → 工程規格 → InkBridge 獨立重製 → 對照測試 → 對實際差距補查。**

### 先確認

遇到操作、功能、資料或效能上的疑點，先找既有分析、切片定位、版本／hash、原版使用者流程及 Gemini 證據。已有充分證據就沿用；不足才做範圍明確的靜態 REA，必要時在安全隔離環境觀察原版 runtime。不啟動會接觸正式 profile 的原版來「試看看」。

查到模組或 API 名稱只證明存在，還要確認條件、輸入輸出、狀態切換與例外；程式機制不等於量測效能。功能清單與研究報告也可能有錯，必須交叉核對，不能因另一個模型寫了就直接接受。

### 按已確認方式重製

將原版行為轉成規格：使用者觸發、正常結果、保存邊界、取消／失敗行為，以及可重複的驗收方式。介面、手勢、快捷鍵、編輯與白板切換等都屬於目標，不能只保留相似技術名詞。

InkBridge 使用自己的可維護原始碼與公開依賴實作。可以忠實重現已研究的設計與操作，不直接搬進專有模組、打包程式或原版二進位；資料庫、附件與設定獨立。研究片段保留在私人研究資料，不加入公開／產品交付 Git 歷史。

### 確認查不到，才自行設計

「查不到」不能是尚未查、工具暫時失敗、只搜了一個名稱，或實作不方便。記錄實際查過的來源／模組／範圍、結果、存取或版本限制，說明哪些細節仍無法確認。無須為此無限制重做整份逆向，但不能憑空宣稱已查清。

在該功能的紀錄中分列：原版已知事實、未確認點、自行補足的暫定方案、影響和驗證方法。日後取得原版證據，再比較並調整；不得把暫定方案回寫成原版事實，也不為方便偷偷改變產品目標。

### 驗證差距

修改前保留 Git 基線、相關歷史回歸及必要效能結果。自己程式的 bug 先重現，再用實際呼叫邊界測試與量測定位原因；只有原版行為未知才補相應 REA，不靠猜測修程式。

修改後區分：單元／合成測試、真實 Electron／封裝版操作、原版 runtime 對照，以及尚未驗證。範圍、場景、樣本、版本與 hash 可追溯；未量測不宣稱性能相同，不把框線對齊說成全部文字排版完全一致。測試通過才標示該驗收項目完成；仍有差距就明列。

## 本次已知差距的示例

- 密集 500 卡連續縮放仍掉幀：已有 raw timing／record／flush 證據，整個長停頓的成因尚未全部確認。下一步先 profiler 並對照相關 REA，不直接套用整批雙層重寫。
- 公開 Lexical 的可選 undefined 欄位造成 JSON 拒絕：以真實編輯器輸出和 SQLite 回歸確認，修正 JSON 邊界；沒有把它誤歸因為 FlexNote REA 不足。
- Gemini 功能清單仍在整理：保留草稿，不把其中「DONE」或範圍排除直接當成使用者已驗收／新指令；逐項對照 InkBridge 原始碼和測試。

本流程不取消既有快照／資料自主目標，也不在 M2 擴展 OneDrive 或完整快照 GUI；功能順序後續根據已確認的原版清單與使用者優先級安排。
