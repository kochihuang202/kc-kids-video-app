# Cloudflare 存取與認證排查 SOP

本專案使用本機 Wrangler OAuth 登入。沒有 Cloudflare 外掛不代表不能存取 Cloudflare；也不能只憑受限環境中的一次失敗要求使用者重新登入。

## 檢查順序

1. 先讀取專案的 `wrangler.jsonc` 與相關部署／上傳文件，確認目標 Worker、R2 與 D1；不要讀出或輸出憑證檔內容。
2. 在專案根目錄執行唯讀檢查：

   ```powershell
   .\node_modules\.bin\wrangler.cmd whoami
   ```

3. 若出現 `EPERM`、存取拒絕、網路限制、OAuth token expired／could not be refreshed，先辨識是否為執行環境限制。依工具的核准流程，以完整本機權限重跑相同的唯讀檢查，讓既有 OAuth 憑證有機會正常更新。不得繞過核准限制。
4. 成功回報帳號與權限後，沿用既有登入；以檢查結果判斷所需操作是否可用。`whoami` 成功不代表每個 R2 或 D1 資源都已驗證可存取。
5. 完整權限檢查仍認證失敗時，才依實際錯誤處理重新登入或權限不足。無法取得完整權限時，告知「尚未確認」，不要斷言必須重新登入。

## 操作界線

- `whoami` 不部署網站、不上傳素材、不修改遠端資料；工具可能更新本機 OAuth 憑證與日誌。
- 不輸出 OAuth token、refresh token、API token，也不把憑證放入 Git 或文件。
- 不因排查認證而更換帳號、清除憑證或建立新的 API token。
- 網站能正常使用與本機 CLI 能否存取是不同狀態；應分別說明。
- 上傳與部署仍遵循當次使用者授權及既有流程；正式 D1 更新前依上傳流程備份。

## 已確認案例

2026-10-11：受限環境中的 `whoami` 同時回報日誌寫入 `EPERM` 及 OAuth 憑證無法更新；改用完整本機權限後，原有 OAuth 登入成功，無需使用者重新登入。此案例不能推論每次認證錯誤都由沙箱造成，仍須依上述順序驗證。
